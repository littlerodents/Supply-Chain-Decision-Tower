# 我们踩过的坑：诚实记录

> 每一个坑都真实发生过。记录它们不是为了找借口，是为了下次不再踩。

## 坑 1：环境变量继承导致子进程静默失败

**时间**：9/27 15:45
**场景**：Streamlit 面板调用 openclaw CLI
**症状**：JSONDecodeError，openclaw 无输出

**根因**：面板服务进程是早期启动的，环境变量中没有 `~/node26/bin`。openclaw 的 shebang 是 `#!/usr/bin/env node`，找不到 `node` 就直接失败、零输出，`json.loads('')` 崩溃。

**为什么没提前发现**：测试跑在自己的 shell 里（PATH 完整），没测服务进程环境。

**如果重来**：所有子进程调用应该显式注入 `env=dict(os.environ, PATH=...)`，不依赖父进程环境。

## 坑 2：Streamlit 长等待期间用户操作取消渲染

**时间**：9/27 16:30
**场景**：Agent 决策需 40-90 秒，用户在等待期间点击了其它控件
**症状**：计算完成但界面不显示结果，看起来像"没有任何反应"

**根因**：Streamlit 在一次长时间运行期间，用户点击任何控件会**取消当次渲染**。结果算完了但显示被取消，用户看不到。

**修复**：结果存入 `session_state`，下一次任意交互自动恢复显示。加了 `skip_restore_once` 防止重复渲染。

**如果重来**：第一天就应该用异步模式或禁用 UI，而不是等用户报 bug 后再修。

---

## 坑 3：SKILL.md 被队友覆盖

**时间**：9/27 20:45
**场景**：前端联调期间
**症状**：live Agent 全线 UNPROVEN（模型突然不输出 JSON 了）

**根因**：有人（队友/另一个会话）用自己写的 SKILL.md 替换了冻结版——包含完全不同的 SOP（REPLENISH/安全股/LT 风格），引用了不存在的数据文件。模型照着新说明书走，自然吐不出我们的八字段 JSON。

**修复**：从 git 仓库副本恢复，实测验证（JSON 围栏回归）。

**如果重来**：
1. 冻结文件应该设为只读（`chmod 444`）
2. 建立变更流程：任何改动必须走 PR + diff + 回归测试
3. 多会话/多人协作时应该有文件锁或版本控制钩子

## 坑 4：模型格式不稳定的根本原因误判

**时间**：9/27 深夜～9/28 凌晨
**场景**：Nemotron 120B 五轮调优全部失败
**症状**：模型能算对所有数字，但坚决不输出 ```json 格式的八字段

**误判过程**：
1. 先以为是温度问题 → 降到 0 → 数字稳了但格式没变
2. 再以为是提示词不够强 → 加双语契约 → 无变化
3. 再以为是上下文不够 → few-shot 预热 → 无变化
4. 最终发现：**这是训练出来的行为模式，不是推理时能改的**

**根因**：Nemotron-3-Super 的训练人格是"谨慎分析师"——它倾向于说"此为查询分析结果，如需执行请进一步确认"，而不是直接签发机器合同。这是 NVIDIA 训练目标决定的，推理时改不了。

**如果重来**：在投入大量调优时间之前，先做一个 5 分钟的"能力探测"——给模型一个最简单的 JSON 格式要求，看它能不能稳定遵守。如果不能，直接走适配器路线，不要浪费 5 轮调优。

## 坑 5：148B 部署——101GB 下载后发现运行时不支持

**时间**：9/28 全天
**场景**：下载并部署 Step-3.7-Flash-148B 社区量化版

**过程**：
1. 下载 101GB → ✅（含断点续传修复）
2. 安装 PyTorch + CUDA on aarch64 → ✅
3. 安装 vLLM → ✅
4. 加载模型权重 → ✅（86-94 GiB 进入 GPU）
5. FlashInfer MoE 内核编译 → 手动预编译成功 → ✅
6. vLLM 引擎初始化 → ❌（Triton GCC 编译错误，连续多轮失败）

**根因**：NVFP4 量化格式是 Blackwell 原生的，但 **aarch64 上的开源推理栈（PyTorch/vLLM/Triton）对此支持尚不成熟**。需要 TensorRT-LLM（NVIDIA 专用推理引擎）。

**如果重来**：在下载 101GB 之前，先用 5 分钟检查这个量化格式是否有 aarch64 推理引擎支持。或者先下载一个小得多的测试文件验证整个链路。

## 坑 6：GitHub 推送混乱

**时间**：9/28
**场景**：将代码推送到 GitHub

**过程**：
- 第一次：SSH 密钥问题（Mac 上没有正确配置）
- 第二次：repo 不存在
- 第三次：SSH 可以了但仓库 URL 错了
- 第四次：推成功了但用了 `--force` 覆盖了旧历史
- 第五次：需要从远端恢复旧提交（通过完整 SHA 的 `git fetch`）

**如果重来**：在项目开始时就设好 git 工作流：一个 canonical 仓库、一条主分支、明确的 push/pull 流程。不要在截止前一晚才做第一次 push。

## 坑 7：pkill 自杀

**时间**：9/28 凌晨
**场景**：停止一个卡住的下载进程

**症状**：执行 `pkill -f "nemotron70b"` 后，**当前 bash 会话也被杀了**（因为命令字符串本身包含 "nemotron70b"）。

**如果重来**：用 PID 文件而不是 `pkill -f`，或者至少加 `| grep -v $$` 排除自身。

---

## 坑 8：测试超时导致假阴性

**时间**：9/28
**场景**：综合测试套件中 120B 模型调用

**症状**：3/5 随机测试中模型"超时"，但适配器兜底产出了正确结果

**根因**：120B 在 ollama 上需要 55-323 秒/次。如果模型刚被卸载（keep_alive 过期），重新加载 86GB 需要额外几分钟。600 秒超时经常不够。

**如果重来**：测试前先用一个简单的 `ollama run` 预热模型。所有模型调用加 try/catch 超时保护，超时时标注"模型超时（适配器兜底）"而不是报错。
