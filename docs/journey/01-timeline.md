## 阶段四：本地模型攻坚（9/27 深夜～9/28）

这是我们投入最多、也学到最多的阶段。

### 尝试 1：Nemotron-120B 协议优化

| 干预 | 结果 |
|---|---|
| temp 1.0→0 | 工具调用修复、数字恒对 ✅ 但 JSON 格式仍缺席 |
| `--thinking` | OpenClaw 对该模型仅支持 off（harness 限制） |
| SKILL 双语输出契约 | 无行为变化 |
| SYSTEM 烤入 detailed thinking | 无行为变化 |
| 会话内 few-shot 预热 | 真问轮仍无 JSON |

**结论**：五类干预全负，120B 的协议输出缺口是**能力级**，不是提示词能修的。

### 尝试 2：换更小的 NVIDIA 模型

| 模型 | 结果 |
|---|---|
| Nemotron-70B-Instruct Q4 | 0/3 全超时（601s×3，工具循环 24/9/27 调） |

### 尝试 3：StepFun 本地化

| 版本 | 大小 | 119GB 内存 | 结果 |
|---|---|---|---|
| BF16 官方 | 402.7GB | ❌ 超 238% | 不可行 |
| FP8 官方 | 212.5GB | ❌ 超 78% | 不可行 |
| NVFP4 官方 | 129.3GB | ❌ 超 10% | 不可行 |
| 0xSero 148B 社区版 | 101.0GB | ⚠️ 勉强可装 | **vLLM 部署失败**（详见下） |

### 148B 部署过程（投入大量时间的失败）

1. ✅ 下载 101GB（含断点续传修复）
2. ✅ 安装 PyTorch 2.14+cu130 on aarch64
3. ✅ 安装 vLLM 0.30.0
4. ✅ 模型权重加载（86-94 GiB 全部进入 GPU）
5. ✅ FlashInfer MoE 内核预编译（手动 ninja，解决了 OOM）
6. ❌ vLLM 内存分析阶段失败（Triton GCC 编译错误）
7. ❌ 最终未能产出推理结果

**结论**：NVFP4 量化模型需要 TensorRT-LLM（专用推理引擎），标准 PyTorch/vLLM 尚不完全支持 aarch64 上的此格式。

### 突破：适配器架构

**转折点**：放弃让 120B 输出 JSON，改为"120B 管推理 + Python 管合同"。

```
问句 → 120B 调工具(gap/suppliers/shipping) → Python 适配器组装八字段 JSON
                                            → Python 确定性审计（逐字段对比）
```

**首次全绿**：决策 ✅ + 审计 ✅ + 负例 ✅ = 3/3，零云端。

## 阶段六：ROP 升级（9/28 深夜）

从"裸缺口补货"升级为"ROP 驱动的预防性补货"。

- gap 计算：`stock - demand` → `ROP - stock`
- 订量：`-gap`（补全缺口）→ `rop_gap + safety_stock`（补到安全水位）
- 示例：13001@SF 12周从订 3268 件降为 359 件（减少过度库存 89%）
- 安全库存：σ(周波动) × z(95%服务水平) × √L(提前期)
