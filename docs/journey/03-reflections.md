# 反思：如果重来一次

> 不是后悔，是学习。每个"如果"背后都有一个可以传承的教训。

## 1. 适配器架构应该从第一天就是默认选择

**当时做了什么**：花了 5 轮调优试图让 Nemotron 120B 直接输出八字段 JSON，全部失败后才转向适配器。

**如果重来**：第一天就写适配器。模型的职责是"调工具+推理叙述"，不是"格式化输出"。格式合同由确定性代码保证，这才是正确的职责分离。

**为什么当时没这么做**：我们一开始用 StepFun（云端），它能直接输出正确格式，所以假设本地模型也应该能。没考虑到不同模型的"训练人格"差异。

**传承教训**：在选择技术方案时，先问"这个组件最擅长什么"，再问"怎么让各组件做最擅长的事"。不要假设一个组件能做所有事。

---

## 2. 环境测试应该覆盖服务进程，不只是开发 shell

**当时做了什么**：在自己的终端里测试通过就认为部署没问题。结果面板服务的环境变量缺 `~/node26/bin`，openclaw 子进程静默失败。

**如果重来**：写一个"服务环境检查脚本"，在任何服务启动前自动验证：PATH、Python 版本、关键依赖、子进程可达性。

**传承教训**：开发环境 ≠ 运行环境。部署后必须用运行环境做冒烟测试。

---

## 3. 冻结文件需要技术保护，不只是口头约定

**当时做了什么**：口头宣布"后端冻结"，但没有技术手段保护。队友用另一个版本覆盖了 SKILL.md，导致全线故障。

**如果重来**：
- `chmod 444` 设为只读
- git hooks 阻止直接 push 到冻结分支
- 关键文件用 SHA256 校验和持续监控

**传承教训**：在多人协作中，"约定"不如"技术约束"可靠。如果要冻结，就真的冻结。

---

## 4. 大文件下载前先验证全链路

**当时做了什么**：下载了 101GB 的 148B 模型，花了几小时安装 PyTorch/vLLM，最后发现 aarch64 上 NVFP4 推理栈不成熟。

**如果重来**：先用一个 1GB 的小模型验证整个推理链路（下载→加载→推理→输出），确认可行后再下载大文件。

**传承教训**：在做大规模投入之前，用最小可行验证（MVP）确认路径可行。"Measure twice, cut once."

---

## 5. 用户反馈驱动的开发效率极高，但需要更好的 bug 报告流程

**当时做了什么**：owner 手动测试面板，发现 8 个问题（周期错位、无记录提示、下拉不联动、图表直线等），每个都是口头/截图报告。

**如果重来**：第一天就搭好自动化的 UI 测试（AppTest 或 Playwright），把用户测试留给"体验问题"而不是"功能 bug"。功能 bug 应该在 CI 里被抓住。

**传承教训**：人工测试发现的 bug 数量与自动化测试覆盖度成反比。投入自动化测试的每一分钟都在节省后续人工测试的十分钟。

---

## 6. 混合架构的"云端部分"和"本地部分"的叙事应该更早分离

**当时做了什么**：一开始把"StepFun 云端"和"Nemotron 本地"放在同一个叙事里，导致评委/用户困惑"到底用哪个"。

**如果重来**：从第一天就把两种模式作为独立的产品特性来设计和沟通——"工具直算模式（秒回，离线可用）"和"Agent 模式（30-120 秒，深度推理）"，而不是"本地模式"和"云端模式"。

**传承教训**：用户关心的是"什么时候用什么"，不是"底层用的是谁的模型"。产品叙事应该按用户场景组织，不按技术栈组织。

---

## 7. ROP/安全库存应该更早集成

**当时做了什么**：在截止前最后几小时才把 ROP 接入决策路径，只做了一轮 192 参数扫描，没做多轮回归。

**如果重来**：在搭建工具层的第一天就把 ROP/安全库存作为默认决策逻辑（而不是裸缺口），这样所有后续测试（gold 评测、综合测试、面板测试）都自动覆盖 ROP。

**传承教训**：核心算法应该在基础设施之前确定。如果算法会变，基础设施就应该预留切换空间。我们的"算法插槽"设计是对的，但插入时机太晚。

---

## 8. 过程记录应该实时写，不是最后补

**当时做了什么**：在项目最后阶段才写这份过程记录，很多细节靠回忆。

**如果重来**：每天结束前花 10 分钟写"今日遇到的问题+学到的教训"，用 git commit 的 body 自动记录。

**传承教训**：记忆会美化过程。实时的诚实记录比事后的完美叙事更有价值——对团队和对自己。
