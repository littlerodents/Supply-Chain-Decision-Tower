## 摘要

十天里，我们把 GitHub 上一个真实的 FDE 行业案例——tensor-house 里的供应链控制塔 `control_center_llm`——转化成了一个人人可装的 Agent Skill。运营者问一句"这个仓的这款货未来 12 周够不够卖"，智能体按 SOP 调用只读工具查库存、按再订货点（ROP）算缺口、比较供应商单价和运费，交出一份八字段决策单；库存够的时候，它只说一句"不用补"。

整套系统跑在一台 DGX Spark 上：本地 Nemotron-3-Super 120B 负责推理，Python 适配器保证输出契约，第二个智能体独立复算、逐字段审计，StepFun step-3.7-flash 只作云端备用。这篇文章按时间记下我们怎么选题、怎么改道、怎么在一台租来的机器上把"可验证"一点点做出来，也记下走过的弯路。

## 一、出发点

MIT NANDA 有份报告说，企业 AI 项目里 95% 没产出能进报表的价值；差不多同一时间，FDE（前线部署工程师）的岗位需求一年涨了七倍。这两句话是我们选题时的坐标：缺的从来不是模型，是把模型塞进真实业务、并且能沉淀成别人也能用的东西的那层活。

这次赛题正好是「把已有的 FDE 行业案例转化为 Agent Skill」。我们手里有的是：三个人，一台租来的 DGX Spark（GB10，119GB 统一内存），和每天能凑出来的三个小时。

## 二、参赛历程

### 第一幕 · 定方向（9/20 – 9/23）

**9/20 开营：先读规则。**第一天没写代码。评分表六栏——落地价值与技术创新 25%、智能体与模型优化深度 25%、项目完整性 20%、平台适配 15%、演示效果 10%、赛事征文 5%——我们对着表做的事，是把每一栏翻译成"我们能拿出什么证据"：落地得有真实行业数据，平台适配得有真跑在 Spark 上的东西，完整性得有能复现的评测。这张清单后来长成了我们的台账。机器自己租了一台 4T 版，租到 29 号；SSH 还在机主那儿，要等动员会当面拿。那天记下的一句话是：这次评的是落地，不是"接上了大模型"。

**9/21 选题锁了，又被我们自己掀了。**定方向的办法只有一个：把想法写成假设，互相拆。第一版题目叫 `repro-pack`——用户丢一段录屏进来，自动产出一份结构化的 bug 复现包。它来自一个观察：AI 时代报 bug 的方式变了，但黑盒 SaaS、瞬态 bug、合规审计这些场景里，录屏仍是唯一证据，只是读证据的已经从人变成了修复 agent。往下推一天，结论就变了：读报告的既然是 agent，要交的就不该是给人读的报告，而是一份机器能消费的合同——字段固定、可校验、能直接进 issue。代码写错了能重构，方向选错了只能重来。

**9/22 通宵。**仓库里最早的提交是 02:27，下一条 03:05——白天各有各的班，开发时间基本就在这个点。一夜之间跑通的东西不少：探针梯子测出 text 1.16s / image 2.88s / video 5.0s，确认视频能以 base64 直接进端点；两颗模型各跑三轮真实输出，主脑候选定为 step-3.7-flash（中位延迟 10.18s 对 15.87s，输出更稳）；正例全链路产出 `bugcard.json` + 3 帧 + `repro.md`；两张故意做坏的红队卡被契约校验拒掉；没有 bug 的录屏末行只回 `NO_BUG_FOUND`，什么都不产出。这一晚定下的两条规矩，后来十天都没破：负例零误触（误触一次算 P0 失败），密钥零提交（只走环境变量，不进 git，也不进群）。

**9/23 白天交接，晚上改道。**白天给队友开权限，把 skill 整目录拷到陌生路径验证自包含，再用 `npx skills add` 装进本地 agent——这条命令当天就抓到一个雷：SKILL.md 的 description 里有个裸冒号，YAML 解析不过。晚上开会，我们做了整个项目最贵的决定：改道。`repro-pack` 做得挺完整，但离"行业落地价值"那条 25% 的轴隔着一层方法论；新方向是把 GitHub 上真实的 FDE 行业案例转化成 Agent Skill，离题眼更近，也更容易被验证。那天台账里写的是：改道不是推倒重来，是把方法论搬上车——负例零误触的红线、换脑三值的解耦、磨合过的 evals 办法都留了下来。期限一天没往后挪。散会时 SSH 到手，回去先跑前置检查：aarch64、2.8T 空盘、CUDA 13、Docker 28 全绿，OpenClaw 和 ffmpeg 装上去，gateway 配好。"题还没锁，机器已经能跑了。"

### 第二幕 · 把案例变成 Skill（9/24 – 9/26）

**9/24 选题研究和施工挤在同一天。**选题只有一条规矩：不许拍脑袋。先顺着范冰的《前线部署工程师》找，案例读得挺爽，但 165 个全是公司叙事，一个都跑不起来。再去找能跑的：谁的仓库里真躺着行业数据、真工具、真界面。筛出四个候选，挨个自我攻击到没有还嘴的余地，档案落在 `docs/topic-deepdive/01-04`。赢的是 tensor-house 里的 `control_center_llm`：数据自带（inventory / products / suppliers 全在仓），界面现成，Apache-2.0 能合规转化，而且它本来就是 FDE 交付物的样子。

晚上开工，我们动了它的架构：

> 上游是让 LLM 在应用里写代码再执行；我们让宿主 agent 自己就是 planner / coder / critic，skill 只提供工具 API、领域知识和输出契约，skill 本体零 LLM 调用。

好处是纯确定性、全可测、模型无关——换主脑只改三个环境变量。移植时顺手修了上游三处缺陷：`hash(sku)` 当随机种子导致预测跨进程对不上（换 `zlib.crc32`）；solver 里 f-string 的双花括号让 SQL 恒查空、库存恒为 0（改参数化查询）；非 UI 模块偷偷 import streamlit（换标准 logging）。三处都进了回归测试，夜里又补上一条回归基线和一张 Bug 队列——测试变绿就算工单关闭，队友零上下文也能接手。

**9/25 四象限。**凌晨三点十一分提交的那份文件，是这十天里我们最想给人看的一页。同一套题（8 个正例 + 3 个负例 + 1 个无关问句，金答案全是工具直算、零人工标注），跑 {裸 prompt, 带 skill} × {云端 step-3.7-flash, 本地 nemotron-120b} 四格：

| | 裸 prompt | 带 skill |
|---|---|---|
| step-3.7-flash（云端） | 2/12 · 4.5s | 12/12 · 6.6s |
| nemotron-120b（GB10 本地） | 2/12 · 28s | 12/12 · 97s |

两颗架构完全不同的模型，裸着的时候以同样的姿势翻车：不调工具，直接编数。装上同一份 skill，双双满贯，负例 3/3 全拒。表之外还学到一件事，叫"触发≠遵守"：带 skill 的模型偶尔会"自信裸答"，知道该调工具，却觉得自己已经知道答案。解法是在 SKILL.md 顶上写死一条红线——凡回答里出现库存、需求、补货量、价格、运费数字，必须先有对应的工具输出，没有工具输出就没有回答。评测口径上，我们把"轮数耗尽"和"答错"分开记账，每一轮结果都公开：LLM 评测单轮跑出满分，很容易高估稳定性。

同一天 skill 装上 Spark，`openclaw skills list` 显示 ready。上机踩了三个坑，都当场排掉：systemd 单元里环境变量的注入时序、进程名里是连字符不是下划线、`pkill -f` 会把自己那条命令也匹配进去。

**9/26 冻结点 v0.1.0。**从这晚起只修 bug、不加功能。我们给自己列了一张"不做"的清单：一键重跑 runner、cuDF 数据层、NIM 第二脑、Hermes 可移植性，一个都不吃；新想法写进台账，不进代码。事后看，这天最像工程。

### 第三幕 · 把"可信"做出来（9/27 – 9/28）

**第二个智能体：审计。**起因是一道算错的题：评测里模型把总价算成 46368.9，应该是 46389.9——数量、单价、运费全对，只有乘积错。这种错，自查发现不了。所以我们加了第二个 agent：决策 agent 交八字段决策单，审计 agent 的红线是禁止采信被审单上的任何数字，必须自己重调一遍工具链复算、逐字段对账。把那笔错单喂进去，它返回 `FAIL, mismatches:[{field: total_cost, claimed: 46368.9, recomputed: 46389.9}]`。审计者的价值不在"多一个模型"，在于它必须重新算，而不是再看一遍。

接着拿失败样本收紧 SOP 四次——强制用 `python3` 实算总价、"这一周"消歧成 1 周、正例结尾只留唯一的 JSON 代码块、禁掉"如上已给出"这种省略——每种失败模式都走完"失败样本 → SOP 收紧 → 复测"的闭环，终轮 12/12，60 份原始 JSON 全留档。数据从 3 个 SKU 扩到 48 个，专门塞了两道"运费翻转"题：单价最低的那家加上运费反而更贵，只按单价排序的实现必选错。

**产品面。**面板扩成四种模式：每日巡检（64 个组合一次扫完，短缺按金额排序，运费翻转标星，工具直算、秒级、零模型成本）、工具证据（没记录的组合只说"无记录"，不把未知当零库存）、实时 Agent、上传自己的数据（AI 建议列映射、人工确认、确定性校验）。FIELDWORK 新前端也接了上来，工具层和整条双智能体流水线按 MCP 协议挂出去，7 个工具，任意外部 agent 一句 `reorder_decision(question)`，拿到的就是"出单 → 核算 → 审计"的完整决策包。

**本地模型攻坚。**这是我们投入最多、也学到最多的一段。本地 120B 能调对工具、算对每一个数，却始终不肯按格式交出那份 JSON。我们试了五类干预——温度降到 0、双语输出契约、系统提示、few-shot 预热、思考模式——全部无效，结论是这个缺口在能力层面，不是提示词能修的。又试了更小的 Nemotron-70B（三题全超时），还花了一整晚尝试在单台 GB10 上部署 148B 量化版：权重已全部加载进 GPU，最后卡在 vLLM 的内存分析阶段。

转折点来得很朴素：**不再逼模型输出合同，改成"120B 管推理，Python 管合同"。**模型负责调工具、推理、写结论，适配器按工具输出组装八字段契约，审计再确定性复核一遍。这一改，决策、审计、负例第一次在零云端的情况下全绿。平台这一栏也就不止一段话了：120B 常驻 119GB 统一内存，数据、工具、面板、模型全在一台机器上，库存和供应商价格不出机器；GB10 上用 CUDA 13.0 写了一个批量缺口核算 kernel（100 万组合），Nsight Systems 留了 timeline。

**ROP 升级。**28 号深夜，我们把补货口径从"补齐缺口"升级成"按再订货点预防性补货"：ROP = μ×L + z×σ×√L（95% 服务水平），订量 = rop_gap + 安全库存。同一个问题，SKU 13001 在旧金山仓未来 12 周：补齐缺口要订 3268 件，按 ROP 只需 302 + 57.4 = **359.4 件**，少订 89%，总成本 $13,118.10。

### 第四幕 · 收口与交付（9/29）

最后一天的关键词是减法。README 写满部署说明、技术栈和转化说明；仓库零密钥扫描 0 命中；上游署名与修改点声明补齐（原样快照放在 `case/`，带 ATTRIBUTION）；AI 生成内容按平台规范标注。

演示视频是最后一天在那台租来的机器上录的：DGX 平台 → 终端里本地 120B 的正例决策单 → 负例 NO REORDER → FIELDWORK 前端从工具核算到 Agent 决策 → 决策单。录制时我们守了一条规矩：本地模型任务一次只跑一个。三个 120B 任务并发时，单个任务会被拖到超时上限——这件事也是那天现场学到的。

表单里的东西基本都是现取的：摘要按栏位字数选版本，技术栈抄 README，亮点对着评分表一条条写，没有一句是新编的。

## 三、我们交出了什么

一句话：**一句人话进来，一份带工具证据的决策单出去；不该补的时候，它会说"不"。**

- **Skill 本体**：SKILL.md（SOP + 红线 + 输出契约）+ 7 个只读工具，本体零 LLM 调用，换主脑只改三个环境变量；
- **双智能体**：决策智能体出单，审计智能体独立复算、逐字段对账，错一笔就 FAIL；
- **负例纪律**：库存够时只回 NO REORDER，不给补货量，不推荐供应商；无库存记录时如实说"无记录"，不把未知当成零；
- **本地算力全栈**：Nemotron-3-Super 120B + 适配器契约 + 确定性审计全部跑在 DGX Spark 上，StepFun 仅作备用；
- **产品层**：Streamlit 四模式面板、FIELDWORK 前端、MCP 接口（7 工具）、上传自有数据；
- **可复核的证据**：2×2 评测矩阵五轮全量留档，60 份任务原始 JSON，扩展集 16/16，全部附命令与输出。

## 四、诚实的清单：没做成的事

我们在仓库里专门留了一份踩坑记录，这里挑三件：

1. **本地 120B 的输出格式**：五类干预全部无效，最后靠适配器架构绕过，而不是修好了模型。回头看，适配器应该从第一天就是默认设计。
2. **148B 本地部署**：下载 101GB、装好 aarch64 的 PyTorch 与 vLLM、权重全部进了 GPU，最后卡在编译环节，没有产出推理结果。
3. **协作中的冻结文件被覆盖**：9/27 晚，SKILL.md 被另一份版本替换，线上 Agent 一度全线失效。从 git 副本恢复后，我们的教训是冻结文件要有技术保护，不能只靠口头约定。

## 五、十天带走的几条经验

- **选题是唯一不能"先做起来再说"的东西。**改道那晚成本最高，也最值。
- **评测口径要先于结果。**"轮数耗尽"和"答错"分开记，单轮满分不等于稳定。
- **可验证比更聪明重要。**大模型进决策场景的第一步，是让输出可验证、可拒绝、可追责——审计 agent 必须重新算，而不是再看一遍。
- **把确定的交给代码，把不确定的交给模型。**适配器架构是我们在本地模型上碰壁之后才学会的分工。
- **负例是产品的一部分。**敢说"不"，才谈得上被信任。

## 结语

十天，一次选题改道，一次架构反转，四轮 SOP 收紧，一次口径升级。我们没有做出一个更会说话的模型，而是做了一套让模型说的每个数字都有出处、说错了会被拦下、该说"不"的时候敢说"不"的流程。感谢 NVIDIA 与主办方提供的 DGX Spark 和这个赛题，也感谢 tensor-house 的开源案例让我们有真实的数据可以站在上面。
