## 一句话介绍（≤50 字）

> 在 DGX Spark 上用一句自然语言完成补货决策：智能体调工具查证、输出结构化决策单，库存充足时敢说"不补"。

## 短摘要（~120 字，适合表单"项目简介"栏）

供应链控制塔把运营者的一句问句变成可验证的补货决策。智能体按 SOP 调用 7 个只读工具查库存、算缺口、比供应商运费，输出八字段决策 JSON；库存充足时输出 NO_REORDER、绝不乱给建议。决策与审计全栈跑在 DGX Spark 本地（120B 推理+适配器契约+确定性审计），云端模型仅作可选辅助。

## 长摘要（~300 字，适合"项目详情"栏）

库存补货决策的痛点不是缺数据，而是"看得见报表、做不出决策"：ERP 能算出缺口，但把缺口变成"找哪家供应商、下单多少、总成本几何"仍靠人工。直接问大模型又会 hallucinate 出不存在的价格与供应商。

我们在 DGX Spark 上构建供应链控制塔智能体：运营者一句自然语言问句进来，OpenClaw 网关内的智能体按 Skill SOP 依次调用 gap（缺口）、suppliers（供应商比价）、shipping（运费）等 7 个只读工具，每个数字必须有工具输出作证据，最终输出八字段结构化决策单（SKU/仓库/周期/订量/供应商/单价/运费/总成本）；库存充足时末行输出 NO_REORDER，绝不给出任何补货建议。

架构上以本地算力为主：库存数据、工具链、可视化面板与 120B 模型全部运行在 DGX Spark 本地，敏感数据不出机器；推理由本地 Nemotron-120B 负责，八字段契约由 Python 适配器保证、确定性审计复核——裸模型直跑只有 1/3，适配器架构下 17 项测试全绿（参数扫描 192、随机参数 53、E2E 5、消融 5）；云端 StepFun step-3.7-flash 仅作可选辅助路由（12/12 评测）。

供应链决策 · 智能体 · 工具调用 · 可验证输出 · DGX Spark · StepFun · OpenClaw · Skill

## 技术栈

- 硬件：NVIDIA DGX Spark（GB10 Grace Blackwell，119GB 统一内存，CUDA 13.0）
- 智能体框架：OpenClaw（网关 + 会话 + Skill 机制，systemd 常驻）
- 决策推理：Nemotron-120B（本地）+ Python 适配器契约；云端可选路由：StepFun step-3.7-flash（当前默认，12/12 评测）
- 本地模型：nemotron-3-super:120b-a12b（86GB，ollama）——推理由本地模型负责，契约合规由 Python 适配器与确定性审计保证
- 工具层：Python CLI 工具 7 个（gap/inventory/suppliers/forecast/shipping/chart/kb），SQLite/CSV 数据，全部只读、JSON 输出
- 前端：Streamlit 控制塔面板（:8501）
- 上游：衍生自 ikatsov/tensor-house control_center_llm（Apache-2.0），移植中修复上游 3 处 bug

## 五个亮点（对着评分表写的）

1. **机器可验证的决策协议**：正例必须输出完整八字段决策 JSON，负例末行必须纯文本 NO_REORDER:100——LLM 的回答变成可程序化判定的合同，回应"行业不敢让大模型做决策"的信任痛点。
2. **"没有工具输出就没有回答"**：任何库存/价格/运费数字必须先有工具证据，从 SOP 层面禁止凭记忆作答。
3. **评测门控**：12 项黄金任务机器判分（金答案全部工具直算、零手填）+ 17 项全面测试（参数扫描/随机参数/E2E/消融），原始 JSON 证据链留档，用数据而不是感觉说话。
4. **本地算力全栈**：敏感库存数据、工具链、面板、86GB 的 120B 模型全在 DGX Spark 本地（119GB 统一内存常驻、可秒切），补货扫描用自写 CUDA kernel 百万组合批量核算——决策、审计、数据一台机器闭环。
5. **会说"不"的智能体**：负例纪律（库存够绝不产建议）是演示里最有说服力的信任镜头。
