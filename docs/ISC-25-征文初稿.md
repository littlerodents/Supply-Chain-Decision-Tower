## 会说"不"的补货智能体：DGX Spark 上的供应链控制塔

### 一、从一个真实的尴尬说起

几乎所有做过供应链的运营都遇到过同一个尴尬：报表里什么都有——库存、预测、供应商、运费——但"这个 SKU 这十二周到底该不该补、补多少、找谁补、总共花多少钱"这个决策，还是要人把数字抄到 Excel 里再算一遍。把这个问题直接丢给大模型，它会热情地给你一个答案，价格可能是编的，供应商可能是虚构的，而且库存明明充足，它也总要"建议适度补货"以显得有用。

行业不敢让大模型做决策，不是因为它不够聪明，而是因为它的输出**无法被验证、也无法被追责**。我们这个项目就针对这一点：把补货决策做成一份**机器可验证的合同**。

### 二、系统一分钟

供应链控制塔运行在 DGX Spark 上：OpenClaw 网关以 systemd 服务常驻，运营者用一句自然语言提问，比如"San Francisco 仓库 SKU 13001 未来 12 周够卖吗？需要补货吗？"。智能体按 Skill 中写死的 SOP 依次调用 gap（缺口）、suppliers（供应商比价）、shipping（运费）等七个只读工具，最后输出一份八字段决策 JSON——决策、SKU、仓库、周期、订量、供应商、单价加运费、总成本，附 rationale 和 tool_trace。库存充足时，末行输出纯文本 `NO_REORDER:100`，明确告知盈余 100 件，并且**不给任何补货建议**。

架构是混合的：库存数据、工具链、Streamlit 控制塔面板、两颗开源模型（120B 与 30B）全部在 DGX Spark 本地运行，敏感数据不出机器；决策脑选用 StepFun 阶跃星辰 step-3.7-flash。为什么这样分工，是测出来的，见下文。

### 三、核心设计：可验证的决策协议

这个项目最重要的产出不是某个工具，而是三个写进 SOP 的硬约束：

**第一，没有工具输出，就没有回答。** 凡回答中出现库存、需求、补货量、价格、运费数字，必须先有对应工具输出作证据，禁止凭记忆或估算作答。这一条直接封死了幻觉数字的生存空间。

**第二，正例输出八字段决策 JSON，字段残缺即不通过。** 结构化让下游系统（ERP、审批流）可以程序化消费这份"决策单"，而不是让人去读一段散文。

**第三，负例纪律：库存充足时绝不产建议。** gap ≥ 0 时只输出 `NO_REORDER:<盈余>`，禁止给出任何订量或供应商。传统的 BI 系统很少敢给结论，通用大模型又倾向于"总得建议点什么"——我们让智能体在该拒绝时干脆地拒绝，这是演示中最有说服力的信任时刻。

### 四、评测选型：三腿 A/B 与一次诚实的让位

决策脑选谁？我们没有拍脑袋。设计了三个独立会话的严格判据：两个正例问句必须输出数值完全正确的八字段 JSON（缺口 3268、供应商 Nature Source Coffee、单价 34.5 加运费 2.0、总成本 119282.0）且工具调用零失败；一个负例末行必须是纯文本 `NO_REORDER:100`——带"结论："前缀或括号补充都不算过。

三腿 A/B 的结果：本地 Nemotron 120B 通过 1/3；本地 Qwen3-30B-A3B（MoE）通过 0/2，败因是工具调用失控；StepFun step-3.7-flash 通过 3/3，单轮 13 秒、4 次工具调用零失败。全部原始 JSON 证据留档。

于是有了这个项目最重要的一次让位：**承认本地模型当下过不了严格判据，把决策脑让给 StepFun，同时把数据主权留在 DGX Spark 本地。** 库存数据和工具不出机器，86GB 的 120B 模型照样塞在 119GB 统一内存里随时可切回——本地轴保住"数据不出域"的底线，云脑负责决策质量。我们认为这种"评测门控 + 混合分工"比硬凑"全本地"更诚实，也更接近真实企业会做的选择。

### 五、工程细节

底层数据与求解器衍生自 tensor-house 的 control_center_llm 案例（Apache-2.0），移植中修复了上游三处 bug：跨进程 hash 不稳定导致预测与运费结果漂移、solver 的 f-string 缺陷导致库存恒为 0、Streamlit 隐式依赖缺失。Skill 示例中的总成本与工具实算值曾差 2 美元（119284 vs 119282.0），已对齐——这个 2 美元的偏差若不修，演示里模型照抄示例就会在判据上翻车。另有一套 gold 评测集用于回归。

### 六、写在最后

这个项目想证明的东西很简单：大模型进入决策场景的第一步，不是让它更聪明，而是让它的输出**可验证、可拒绝、可追责**。一句问话进来，一份带工具证据的决策单出去；不该补的时候，它会说"不"。
