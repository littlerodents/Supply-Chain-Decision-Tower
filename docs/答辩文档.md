## 一、技术实现·架构创新（25%）

### 1.1 怎么实现的（HOW，一段话）

自然语言问句进入 DGX Spark 上常驻的 OpenClaw 网关，决策智能体（main）按 `supply-chain-control-tower` skill 的 SOP 调用 7 个只读工具（gap/inventory/suppliers/forecast/shipping/chart/kb，Python+SQLite/CSV，JSON 输出），产出八字段决策 JSON；审计智能体（auditor）以该决策单为"待验证主张"，独立重调同一工具链复算并逐字段对账，输出 PASS/FAIL 判定。数据、工具、Streamlit 面板（:8501）与两颗开源模型（120B/30B）全部在 DGX Spark 本地；决策脑为 StepFun step-3.7-flash。

### 1.2 为什么这么实现（WHY，三个三段论）

**抉择一：工具直算 + 协议约束，而非裸 LLM 直答**
- 大前提：LLM 对具体数值的生成不可靠（幻觉），而企业决策要求每个数字可追溯；"没有数据支撑的决策是赌博"是供应链行业公理。
- 小前提：本场景每个数字（库存/需求/单价/运费）在本地库中都有权威源，可被工具确定性取得。
- 结论：模型只承担编排与表述，数字必须来自工具输出——SOP 第一红线"没有工具输出，就没有回答"。
- 实证：三轮 36 次任务跑中仅有的两笔实质数值错误，恰是模型绕过工具"心算总价"产生的（46369.9/46368.9 vs 应为 46389.9）；SOP 强制 `python3` 实算总价后，该任务在第三轮转为 PASS。**错误样本反向证明了设计前提。**

**抉择二：SOP 沉淀为 skill，而非长提示词**
- 大前提：流程可靠性的来源是确定性约束的可复用、可审计的沉淀，不是一次性提示的运气；提示词不可回归测试，skill 可以。
- 小前提：补货决策规则稳定（周期不明先问→算缺口→比价含运费→总单价最低→八字段单；充足则 NO_REORDER）。
- 结论：规则写成带正/负触发器和红线的 skill，跨会话、跨模型、跨智能体执行同一协议。
- 实证：skill 是 load-bearing 的——示例总成本 2 美元偏差（119284→119282.0）的修复直接决定正例判据通过与否；三腿 A/B 之所以可比，正因为共用同一 skill。

**抉择三：混合架构（本地轴 + 云脑），而非纯本地或纯云**
- 大前提：供应链数据（供应商价格=商业机密）的敏感性使"数据不出域"成为行业落地第一道门槛；同时决策质量直接决定 ROI。
- 小前提：DGX Spark 119GB 统一内存能装下全部数据+工具+开源模型（86GB 的 120B 常驻），但本地脑在严格判据下不过线（Nemotron-120B 1/3、Qwen3-30B-A3B 0/2 且工具调用失控）；StepFun 3/3。
- 结论：数据与工具留在本地、决策脑走云，**用评测数据分工，不用信仰分工**。

### 1.3 好处

可验证（八字段机器判定）、可审计（tool_trace+审计判定）、可复现（独立会话+原始 JSON 留档）、数据不出域、换脑=配置翻转（A/B 在同一台机器完成）。

### 1.4 风险与辩证（诚实清单）

| 风险 | 证据 | 缓解 |
|---|---|---|
| 云依赖（网络/key/配额） | 架构事实 | 本地脑保留可秒级切回；演示有脱网兜底（展示留档 JSON） |
| 模型输出格式方差 | 五轮 9→10→9→11→12：格式类 FAIL 共四种形态，逐一经证据驱动修复归零（终轮 12/12） | 严格判据使方差**可见**而非静默；格式契约入 SOP；审计层二次兜底 |

### 1.5 抉择时间线（局部决策怎么定的）

入口验收（严格判据由 owner 写死）→ 三腿 A/B 证明本地两脑不过线 → owner 拍板混合叙事 → 答辩前补审计层与评测闭环（本轮）。每次转折都有数据支撑，无一处靠感觉。

### 1.6 创新点与已验证算法插槽

核心创新=**机器可验证的决策协议**（正例八字段缺一不可；负例末行纯文本 NO_REORDER 且零建议字段），把 LLM 输出变成可程序化判定的合同。

评测集本身含**对抗性设计**：数据集扩至 6 SKU 后专门构造"运费翻转"任务——单价最低的供应商加上运费后反超（Budget Beans 15.50+7=22.50 vs Golden Gate 19.90+2=21.90；Pacific 24.50+1=25.50 vs Cascade 24.90+0=24.90）。只按 unit_cost 排序的朴素实现必然选错供应商；扩展集 16/16 证明本方案的总单价比较是真实执行的，不是装饰。

按"加入已验证算法增强落地性"的方向，本轮 TDD 实装了经典库存算法插槽（`scripts/algorithms.py` + `test_algorithms.py`，教科书用例 5/5 绿）：
- 安全库存 SS = z·σ·√L；再订货点 ROP = μL+SS；EOQ = √(2DK/h)；报童临界比 Q* = μ+z_{Cu/(Cu+Co)}·σ
- 真实数据 demo：SKU 13001@SF，12 周预测 μ=274.8/周、σ=34.9，95% 服务水平 → SS=57.4、ROP=332.3（现库 30 ≪ ROP，与 REORDER 决策自洽）
- **为什么只做插槽不接入决策路径**：改 gap→ROP 判定会改全部金答案与已验收证据链，deadline 前稳定>功能；且协议分层（工具层换芯，协议/审计/评测层不动）本来就是架构的升级方式。

### 1.7 DGX Spark 充分体现与 1+1>2

- 平台事实：GB10 Grace Blackwell、CUDA 13.0、119GB 统一内存；86GB 120B 常驻可秒切；30B MoE 本地推理实测 SM 利用率峰值 91%（dmon 留档）；Nsight/dgx-dashboard 工具链在位。
- **NVIDIA 软件栈实测**：CUDA 13.0 toolkit（nvcc）在 GB10 上编译运行批量缺口核算 kernel（evidence/cuda-nsys/，100 万组合），并用 Nsight Systems 抓取 CUDA API timeline（cudaMalloc/cudaMemcpy/cudaLaunchKernel 留档）；TRT-LLM 为赛前环境冻结决策（见风险表）。
- 1+1>2 论证：**DGX 让"评测门控选脑"成为一台机器上的配置翻转**（三腿 A/B 在本地完成，不泄数据给第三方评测服务）；**产品让 DGX 不再是闲置 GPU**而是开箱即用的行业场景。无 DGX，数据主权叙事塌陷；无产品，DGX 只是跑分的板子。混合架构里双方各展所长——这正是"合理运用 NVIDIA 技术栈 + 开源模型 + StepFun"的结构性答案。

## 二、多智能体协同·模型优化·Skills·差异化（25%）

### 2.1 协同机制（怎么协同）

流水线交接 + 角色隔离：决策智能体产出八字段单（含 tool_trace）→ 以结构化契约交给审计智能体 → 审计 skill 红线"禁止采信被审单数字"，独立重调同一工具链复算 → 逐字段对账 + 总价自验算（qty×(unit+ship)）+ 负例格式合规 → PASS/FAIL 判定 JSON（mismatches 精确到字段）。两个独立 OpenClaw agent 条目（不同身份/会话/skill），一键脚本 `two-agent-pipeline.sh`。

### 2.2 为什么协同 > 单智能体叠加（三段论 + 实证）

- 大前提：单模型自我检查是**相关失败**（同一上下文、同一偏差，对自己的错误有信心）；去相关的错误检测需要独立取证——工厂"四眼原则"、代码 review 制都是这条公理的制度化。
- 小前提：本项目失败数据显示错误集中于算术与格式，且算术错误模型自查发现不了（r2 那笔错单里，qty/单价/运费全对、只有乘积错——自查会再看一遍自己有信心的乘法）。
- 结论：审计者的价值不在"多一个模型"，而在**错误模式去相关**——它必须重新算，而不是再看一遍。
- 实证（两份留档）：① 审计对正确单六字段全对账 PASS；② 把 r2 算错总价的决策单喂给 auditor，判定 `FAIL, mismatches:[{field: total_cost, claimed:46368.9, recomputed:46389.9}]`，来源会话可追溯。**单 agent 自查场景下，这笔错单会静默流出。**
- 对"为什么协同能驱动模型回答更好"：审计判定是结构化负反馈——FAIL 的 mismatches 指明字段，可直接驱动决策 agent 重取数/重算（路线图：FAIL 自动触发重跑），比"请再检查一下"的语气化反馈强一个数量级。

### 2.3 为什么需要这两个 agent（角色必要性）

- 决策者：编排工具、承担表述责任（产单）。
- 审计者：复算、格式合规、负例红线（验单）。
- 不为多而多：执行下单、多仓网络优化是路线图（需要写权限与更大数据面），当前两角色恰好覆盖"决策可信"这一核心需求。

### 2.4 模型调优深度（为什么调、调了什么、哪里变好）

- **为什么需要调优**：三腿 A/B 显示"未经调优的系统"过不了严格判据（1/3、0/2）；step-3.7-flash 为闭源云模型不可微调，调优空间在**选型、协议、路由**三层。
- **调了什么（全部评测驱动，可复现）**：
  1. 评测门控选脑：12 任务×3 轮机器判分、独立会话、工具直算金答案（gold.json 零手填）。
  2. SOP 收紧×4（每条都有失败样本→修复→复测闭环）：①强制 python 实算总价（pos-dec-004 两轮 FAIL→PASS）；②「这一周」=1 周消歧（neg-stk-001 反问→PASS）；③输出格式契约：正例唯一 ```json 块结尾、负例裸文本末行禁围栏（负例 4 次格式 FAIL→三轮全 PASS）；④禁"已给出"省略与追问/选项结尾（dec-004 r4 形态→PASS）。
  3. 混合路由：本地轴保数据主权，云脑保决策质量。
- **调优后在多智能体场景哪里更优秀**：决策 agent 的实质数值错误率从 2/36 降到 0/12（r3 无算术错）；残余格式方差由审计 agent 兜底——**调优与协同是分层防御，调优消灭已知错误模式，协同拦截未知错误模式。**

### 2.5 Skills 设计与融合

- 为什么这样设计：决策 skill = SOP+正负触发（负触发防天气类问句误触发）+红线+只读工具+示例锚定；审计 skill = 独立取证红线 + UNVERIFIED 标注 + 只判不重开药方。
- 融合：两 skill 共享同一工具层与数据层，靠八字段 JSON 这个**契约格式**串联成流水线，由 OpenClaw 注入会话。
- 怎么提高质量：示例锚定防数值漂移（119282.0 案例）；审计 skill 把"复核"从语气变成可判定输出；skill 可回归测试（gold 评测就是它的测试套件）。

### 2.6 差异化（明确 Baseline）

| Baseline | 失败样本（本项目实测） | 我们的对应层 |
|---|---|---|
| A. 裸 LLM 直答 | 两笔 21/20 美元算术错即样本 | 工具直算+计算器强制 |
| B. RAG（检索后回答） | 能引数据，无决策协议/负例纪律/对账 | 八字段合同+NO_REORDER 纪律 |
| C. 单 agent+工具（无审计） | r2 错单会静默流出 | 审计智能体 FAIL 拦截（已实证） |
| D. 本地脑同 skill | 1/3、0/2 | 评测门控选脑→StepFun 3/3 |

每层的必要性都由上一行的失败样本反证——**方案不是功能堆叠，是对失败模式的逐层设防。**

### 2.7 市场对标与定位（答辩必问）

**定位一句话：ChatBI 回答"是什么"，我们回答"怎么办"。** 我们不做预测引擎、不做优化引擎、不做 ERP——做的是从"报表齐全"到"可追责决策单"的最后一公里，即可验证的决策层。

| 同类产品 | 它们做到哪 | 我们从哪开始 |
|---|---|---|
| 供应链计划套件（SAP IBP / Blue Yonder / o9 / Kinaxis；国内京东、阿里内部平台） | 重数学优化：预测、LP、多级网络。实施以年计、以百万计，服务大型企业 | 它们的产出仍是报表；"一句人话→可追责决策单"的交互层不是其形态。且中小企业完全够不着 |
| ChatBI / 智能问数（Power BI Copilot、Tableau Pulse、阿里 Quick BI 问数、网易有数、Snowflake Cortex） | 自然语言查数出图——覆盖本项目"查询类"任务 | 它们刻意止步于事实（答数不担责）。补货建议涉及采购资金责任，没有 BI 敢输出"买 3268 件、找这家、花 11.9 万"。我们的八字段合同+负例纪律+审计恰是这一层 |
| ERP 内嵌 Copilot / 智能补货 SaaS（Dynamics 365 Copilot、用友 YonGPT、金蝶苍穹 GPT；电商侧聚水潭/秦丝智能补货） | 厂商锁定、闭源黑箱建议，或规则型自动补货 | 我们开源协议模式（Apache-2.0）、本地部署数据不出域、模型可换（StepFun/本地已实测热切换）、建议附工具证据与审计判定，可被下游系统程序化验收 |

**Skill 资产的本质**：skill=数字化的岗位 SOP 合约。Agent 无 skill 是"聪明但不可信"（会编数、会过度建议）；SOP 无 agent 是"没人读的 PDF"。本项目证明 skill 是 load-bearing 的：五轮评测的每一次提升（9→12/12）都是对 SKILL.md 的一次收紧——skill 是行为的控制面，也因此可测试、可回归。

**Agent 原生产品化（MCP）**：工具层与双智能体决策流水线以标准 MCP 协议（stdio/JSON-RPC，零依赖实现）暴露为 7 个可挂载工具——任意外部 Agent（含 coding agent）一句 `reorder_decision(question)` 即获得"决策智能体出单→确定性核算→审计智能体盖章"的完整决策包；这正是"外部 Agent 调工具、工具内 Agent 自治完成工作后返回"的嵌套智能体形态。HLA（IEEE-1516 仿真联邦）等更重协议在比赛窗口内不实施，以 MCP 为标准接入层。

**产品形态（回答"这是演示还是产品"）**：控制塔的日常运营闭环=「📋 每日巡检」一键全组合扫描（48 SKU×64 组合，工具直算秒级零 LLM：短缺排行/运费翻转标记/建议采购总额/报告留档）→ 例外一键转「🤖 实时 Agent」追问（八字段决策单+独立核算+审计盖章）。批量层用确定性工具（规模与成本正确）、语言层用 LLM（交互与解释正确）——这是"Agent 该用在哪"的架构答案，也是与"每问一次调一次模型"的玩具 demo 的本质区别。**Bring-your-own-data**：📤 上传任意工厂 CSV/Excel → AI 建议+人工确认列映射 → 确定性校验与诚实降级（无供应商列只出缺口、无发货地不含运费、无需求列用显式估算）→ 在用户自己的数据上出补货单——信任架构对任意数据成立，映射错误由人确认这道闸拦住。

## 三、完整性（20%）

- 功能：问句→决策单全链路，演示路径 3/3 过 owner 写死的严格判据（正例八字段+工具证据；负例末行纯文本 NO_REORDER:100）。
- 评测：12 任务×5 轮全量留档（终轮 **12/12**）；数据集扩展后 16 任务（含 2 个运费翻转对抗任务 + 1 新负例 + 1 新查询）单轮 **16/16**；含每任务延迟/token/工具失败数。
- 前后端：浏览器 → Streamlit 面板(:8501) **双模式闭环**——🧮 工具证据（零 LLM 直算：6 SKU 动态加载、无记录防护、图题=点数、供应商含运费比价与运费翻转标注）与 🤖 实时 Agent（问句→默认路由→原答/确定性独立核算/审计智能体判定**同屏**；独立会话、单次提交、90s 超时不自动重试）。经 Streamlit AppTest 端到端验证（正例三件套 PASS、无记录组合只警示不给补货结论）；浏览器视觉检查因录制环境无浏览器后端由 owner 录屏时目检兜底。另有 CLI 入口 + 双 skill + 7 工具 + 算法插槽。
- 文档：ISA/STATUS 台账纪律、evidence/ 原始 JSON、README、录屏脚本、本答辩文档、提交检查单。
- 稳定：systemd 常驻；单任务 5-22s；演示兜底预案（live 翻车切留档 JSON 照样成立）。
